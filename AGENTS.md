# ScriptRunner Dev and Deployment Tool - Agent Guide

This project deploys ScriptRunner Cloud configurations (listeners, script fields, jobs, behaviours, workflows, and
Script Manager scripts) from a local Gradle project to a Jira Cloud instance.

Documentation: https://docs.adaptavist.com/sms/latest/scriptrunner-dev-and-deployment-tool

This guide is written for **AI coding assistants** (Cursor, Copilot, Claude, etc.) that need to understand the
repository layout, generate valid `extensions.yaml` entries, and create matching script files.

## Project Structure

```
cloud/src/main/
├── groovy/                    # Groovy scripts: listeners, script fields, jobs, workflows, Script Manager
│   └── <subdirs>/             # Subdirectories supported (e.g. acme/dev/MyScript.groovy)
├── typescript/                # TypeScript scripts for behaviours ONLY
│   └── <subdirs>/             # Subdirectories supported (e.g. subpackagea/behaviourB.ts)
└── resources/
    └── extensions.yaml        # Single source of truth for all deployed configuration
onprem/src/main/groovy/        # Optional DC scripts for comparison — NOT deployed
mapped/<subdomain>/            # Generated by pullMappings — deploy reads from here when present
mappings-<subdomain>.json      # DC→Cloud ID mappings (project root)
gradle.properties              # Target site URL (targetAtlassianSite)
settings.gradle                # Gradle plugin version
```

### Relevant external files

Typically, users will rely on automatic authentication from a browser prompt when running deployment commands, but for
CI
environments, they may want to specify credentials using an Atlassian developer token. These can be written to a file in
the
user home or passed as command line arguments via Gradle's `-P` flag.

```
~/.gradle/gradle.properties               # (Optional) User credentials (atlassianUser, atlassianToken) - NEVER commit
```

## The extensions.yaml File

All ScriptRunner Cloud configuration is defined in `cloud/src/main/resources/extensions.yaml`. This is the single source
of truth for what gets deployed. The top-level keys are:

- `scriptfields` - Scripted fields that compute values on issue screens
- `listeners` - React to Jira webhook events
- `jobs` - Scheduled jobs AND escalation services (escalation services have a `jql` field)
- `behaviours` - TypeScript-based field visibility/validation on issue screens
- `workflows` - Conditions, validators, and post functions on workflow transitions
- `additional-scripts` - Scripts uploaded to Script Manager (not attached to any feature)

### Referencing Scripts in YAML

There are two ways to reference a script:

- **`file`** (preferred for all features except behaviours): Path relative to `cloud/src/main/groovy/`, supports
  subdirectories. Scripts are managed in Script Manager. Example: `file: "acme/dev/MyScript.groovy"`
- **`path`** (behaviours and legacy inline): Filename only, script must be directly in `cloud/src/main/groovy/` and gets
  inlined. For behaviours, this is relative to `cloud/src/main/typescript/`.

### UUID Rules

UUID fields are **identity fields**, not disposable placeholders:

| Rule                  | Detail                                                                                    |
|-----------------------|-------------------------------------------------------------------------------------------|
| Format                | Standard UUID: `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` (hex, with hyphens)                 |
| Preserve on migration | When converting DC configuration, keep existing UUIDs 1:1                                 |
| Generate new          | Only for genuinely new entries or to resolve duplicate collisions                         |
| Applies to            | Top-level `uuid`, behaviour `fieldUuid`, workflow `parameters.id`, workflow `config.uuid` |

When creating a new entry, generate a random UUID v4. When editing an existing deployed entry, **never change its UUID
**.

### YAML conventions

- Use 2-space indentation; lists use `-` items.
- The key is `scriptfields` (all lowercase), not `scriptFields`.
- All top-level keys are optional; omit unused sections entirely.
- Invalid entries are logged and skipped; valid entries still get deploy tasks.
- Comment out entries with `#` to disable without deleting.
- Use `%alias%` placeholders for instance-specific IDs (see [Identifier Mappings](#identifier-mappings)).

## Feature schemas

Each section lists fields, types, constraints, and a minimal valid example. Required fields are marked **(required)**.

### Script fields (`scriptfields`)

Scripted fields compute values displayed on issue screens.

| Field               | Type          | Required              | Notes                                              |
|---------------------|---------------|-----------------------|----------------------------------------------------|
| `uuid`              | string (UUID) | **yes**               | Identity field                                     |
| `name`              | string        | **yes**               | Max 128 characters; used as deploy task identifier |
| `scriptedFieldType` | enum          | **yes**               | See values below                                   |
| `file`              | string        | one of file/codeToRun | Path relative to `cloud/src/main/groovy/`          |
| `codeToRun`         | string        | one of file/codeToRun | Inline Groovy (avoid — prefer `file`)              |
| `description`       | string        | no                    | Human-readable description                         |

**`scriptedFieldType` values:** `TEXT_FIELD`, `NUMBER_FIELD`, `DATE_FIELD`, `DATETIME_FIELD`, `RICH_TEXT_FIELD`

```yaml
scriptfields:
  - uuid: "<uuid>"
    name: "<Field Name>"
    description: "<optional>"
    scriptedFieldType: "TEXT_FIELD"
    file: "<ScriptName>.groovy"           # or acme/dev/<ScriptName>.groovy
```

### Listeners (`listeners`)

Listeners react to Jira webhook events.

| Field                | Type            | Required           | Notes                                                                                  |
|----------------------|-----------------|--------------------|----------------------------------------------------------------------------------------|
| `uuid`               | string (UUID)   | **yes**            | Identity field                                                                         |
| `description`        | string          | **yes**            | Used as deploy task identifier                                                         |
| `events`             | list of strings | **yes**            | Jira webhook event names                                                               |
| `file`               | string          | one of file/script | Path relative to `cloud/src/main/groovy/`                                              |
| `script`             | string          | one of file/script | Inline Groovy (avoid — prefer `file`)                                                  |
| `executionUser`      | enum            | **yes**            | `ADD_ON` or `INITIATING_USER`                                                          |
| `executionCondition` | string          | no                 | Jira Expression Language (JEL); inline                                                 |
| `conditionFile`      | string          | no                 | Path to a `.jel` file in Script Manager (mutually exclusive with `executionCondition`) |
| `projects`           | list of strings | no                 | Project keys to scope listener; omit for all projects. Supports `%project-alias%`      |
| `enabled`            | boolean         | no                 | Default `true`                                                                         |

**Common event values:**

| Event                | When it fires |
|----------------------|---------------|
| `jira:issue_created` | Issue created |
| `jira:issue_updated` | Issue updated |
| `jira:issue_deleted` | Issue deleted |

```yaml
listeners:
  - description: "<What this listener does>"
    uuid: "<uuid>"
    events:
      - jira:issue_created
    file: "<ListenerScript>.groovy"
    executionUser: ADD_ON
    projects: # optional; omit for all projects
      - "<PROJ>"                           # or "%project-alias%"
```

**Execution condition example** (Jira Expression Language):

```yaml
executionCondition: |-
  issue.changelogs[0].items.some(changelogItem =>
      changelogItem.field == 'status'
      && changelogItem.fromString == '<fromStatus>'
      && changelogItem.toString == '<toStatus>'
  )
```

### Jobs and escalation services (`jobs`)

Both scheduled jobs and escalation services share the `jobs` key. The presence of `jql` (Jira) or `cql` (Confluence)
makes an entry an **escalation service**.

| Field            | Type          | Required           | Notes                                                                  |
|------------------|---------------|--------------------|------------------------------------------------------------------------|
| `uuid`           | string (UUID) | **yes**            | Identity field                                                         |
| `name`           | string        | **yes**            | Used as deploy task identifier                                         |
| `cronExpression` | string        | **yes**            | 6-field Quartz cron: `sec min hr dom mon dow`                          |
| `file`           | string        | one of file/script | Path relative to `cloud/src/main/groovy/`                              |
| `script`         | string        | one of file/script | Inline Groovy (avoid — prefer `file`)                                  |
| `atlassianUser`  | object        | **yes**            | `{ accountId: "<account-id>" }` — supports `%user-alias%`              |
| `enabled`        | boolean       | no                 | Default `true`                                                         |
| `jql`            | string        | escalation only    | JQL query; presence of `jql` or `cql` makes this an escalation service |

**Cron expression format** (6 fields, Quartz):

```
0 0 0 1 * ?       # midnight on the 1st of every month
0 0 * ? * *       # every hour
0 0 0 1,15 * ?    # midnight on the 1st and 15th
```

```yaml
jobs:
  # Scheduled job
  - uuid: "<uuid>"
    name: "<Job Name>"
    cronExpression: "0 0 0 1 * ?"
    file: "<JobScript>.groovy"
    atlassianUser:
      accountId: "<account-id>"         # or "%user-alias%"
    enabled: true

  # Escalation service — add jql (or cql) to make it an escalation service
  - uuid: "<uuid>"
    name: "<Escalation Name>"
    cronExpression: "0 0 * ? * *"
    jql: "<JQL query>"
    file: "<EscalationScript>.groovy"
    atlassianUser:
      accountId: "<account-id>"
    enabled: true
```

### Behaviours (`behaviours`)

Behaviours control field visibility, values, and validation on issue screens. They use **TypeScript only** — never
Groovy.

| Field           | Type            | Required | Notes                                                        |
|-----------------|-----------------|----------|--------------------------------------------------------------|
| `uuid`          | string (UUID)   | **yes**  | Identity field                                               |
| `name`          | string          | **yes**  | Must be unique across all behaviours; deploy task identifier |
| `description`   | string          | no       | Human-readable description                                   |
| `enabled`       | boolean         | no       | Default `true`                                               |
| `executionUser` | enum            | no       | `ADD_ON`                                                     |
| `config`        | list of objects | **yes**  | One entry per field the behaviour targets                    |
| `mappings`      | map             | **yes**  | Project key → list of work item type names                   |

**Behaviour `config` entry:**

| Field            | Type            | Required | Notes                                                                     |
|------------------|-----------------|----------|---------------------------------------------------------------------------|
| `fieldUuid`      | string (UUID)   | **yes**  | UI Modification field UUID; must be unique within the behaviour           |
| `fieldName`      | string          | **yes**  | Leave as `""` (empty); resolved via `fieldUuid`                           |
| `path`           | string          | **yes**  | TypeScript file relative to `cloud/src/main/typescript/`                  |
| `event`          | list of enums   | **yes**  | `ONLOAD`, `ONCHANGE`                                                      |
| `viewTypes`      | list of enums   | **yes**  | Where the behaviour runs (see below)                                      |
| `affectedFields` | list of strings | **yes**  | Jira field IDs affected (e.g. `summary`, `description`, custom field IDs) |

**`viewTypes` values** (publicly supported):

| Value             | Screen              |
|-------------------|---------------------|
| `GIC`             | Global Issue Create |
| `IssueView`       | Issue view          |
| `IssueTransition` | Issue transition    |

These are the view types used in this project's `extensions.yaml`. Do not document JSM or Agent view types until they
are publicly supported.

**`mappings` format:** Map of project key → list of work item type names. Use `"all"` as a key to target all projects (
must still specify work item types). Supports `%issueType-alias%` placeholders.

```yaml
behaviours:
  - name: "<Behaviour Name>"
    uuid: "<uuid>"
    description: "<optional>"
    enabled: true
    executionUser: ADD_ON
    config:
      - fieldName: ""
        fieldUuid: "<uuid>"
        path: <behaviourScript>.ts        # or subpackagea/behaviourB.ts
        event:
          - "ONLOAD"
          - "ONCHANGE"
        viewTypes:
          - "GIC"
          - "IssueTransition"
          - "IssueView"
        affectedFields:
          - "summary"
    mappings:
      "<PROJ>":
        - "<IssueType>"
      "all": # wildcard: all projects
        - "<IssueType>"                    # or "%issueType-task%"
```

**Constraints:**

- Two behaviours **cannot share the same name**.
- Each `config` entry must have a **unique `fieldUuid`** within the behaviour.
- TypeScript is compiled to JavaScript before deploy; expected compiler warnings can be ignored.

### Workflows (`workflows`)

Workflow entries attach ScriptRunner conditions, validators, and post-functions to **existing** Jira workflow
transitions. The workflow must already exist in the target Cloud instance (typically migrated via JCMA).

| Field         | Type   | Required | Notes                                         |
|---------------|--------|----------|-----------------------------------------------|
| `name`        | string | **yes**  | Must match the Jira workflow name **exactly** |
| `transitions` | list   | **yes**  | Transitions to configure                      |

**Transition object:**

| Field           | Type          | Required    | Notes                                                                                                                                                        |
|-----------------|---------------|-------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `name`          | string        | **yes**     | Transition name as shown in Jira                                                                                                                             |
| `id`            | string        | conditional | Jira numeric transition ID. Required only when `name` is not unique and status disambiguation is insufficient. Brittle across instances — use as last resort |
| `sourceStatus`  | string        | conditional | Source status **name** (not ID). Required with `targetStatus` when the transition name is ambiguous within the workflow                                      |
| `targetStatus`  | string        | conditional | Target status **name** (not ID). Required with `sourceStatus` when the transition name is ambiguous within the workflow                                      |
| `type`          | enum          | no          | Optional disambiguation: `INITIAL`, `GLOBAL`, or `DIRECTED` — use when `sourceStatus`/`targetStatus` alone are not enough                                    |
| `conditions`    | list or group | no*         | Jira Expression conditions                                                                                                                                   |
| `validators`    | list          | no*         | Jira Expression validators                                                                                                                                   |
| `postFunctions` | list          | no*         | Groovy post-functions                                                                                                                                        |

\*At least one of `conditions`, `validators`, or `postFunctions` should be present — otherwise the transition entry has
nothing to deploy.

**Identifying transitions:** Only `name` is always required. The workflow must already exist in Jira Cloud (typically
migrated via JCMA).

In workflows where more than one transition has the same name, disambiguate using `sourceStatus` and `targetStatus`.
Where necessary, you can also specify a transition `type` (`DIRECTED`, `GLOBAL`, `INITIAL`). Use transition `id` only as
a last resort when name, statuses, and type still aren't enough.

**Two different `id` fields — do not confuse them:**

| Location                                                          | What it is                                 | Required?                               |
|-------------------------------------------------------------------|--------------------------------------------|-----------------------------------------|
| On the **transition object** (`transitions[].id`)                 | Jira's numeric transition ID (e.g. `"21"`) | Only for disambiguation                 |
| On **conditions / validators / post-functions** (`parameters.id`) | ScriptRunner rule identity UUID            | **Yes** — every rule needs a valid UUID |

Each condition, validator, and post-function also requires `config.uuid` (a separate identity UUID for the rule config).

**Transition disambiguation** (when multiple transitions share a name):

1. `id` — highest precedence (brittle across instances; use as last resort)
2. `sourceStatus` + `targetStatus` + optional `type`
3. `name` alone — only when unique within the workflow

**Name only** (transition name is unique in the workflow):

```yaml
transitions:
  - name: "Create"
    validators:
      - parameters:
          id: "<uuid>"                    # ScriptRunner rule UUID — required
          config:
            uuid: "<uuid>"                # config identity UUID — required
            expression: "issue.summary.length >= 5"
            errorMessage: "Summary too short."
            enabled: true
```

**Ambiguous name** (same transition name used more than once — disambiguate with statuses; add `type` if needed):

```yaml
# In workflows where more than one transition has the same name, disambiguate using sourceStatus, targetStatus
# Where necessary, you can also specify a transition type (DIRECTED, GLOBAL, INITIAL)
transitions:
  - name: "Done"
    sourceStatus: "In Progress"
    targetStatus: "Done"
    conditions:
      - parameters:
          id: "<uuid>"
          config:
            uuid: "<uuid>"
            description: "<description>"
            expression: "<JEL expression>"
            enabled: true
  - name: "Done"
    sourceStatus: "To Do"
    targetStatus: "Done"
    conditions:
      - parameters:
          id: "<uuid>"
          config:
            uuid: "<uuid>"
            description: "<description>"
            expression: "<JEL expression>"
            enabled: true
```

**Complete example** (conditions, validators, and post-functions on one transition):

```yaml
workflows:
  - name: "<Exact Workflow Name>"
    transitions:
      - name: "Done"
        sourceStatus: "In Progress"
        targetStatus: "Done"
        conditions:
          - parameters:
              id: "<uuid>"
              config:
                uuid: "<uuid>"
                description: "Assignee must be set"
                expression: "(issue.assignee != null)"
                enabled: true
        validators:
          - parameters:
              id: "<uuid>"
              config:
                uuid: "<uuid>"
                description: "Summary length check"
                expression: "issue.summary.length >= 5"
                errorMessage: "Summary must be at least 5 characters."
                enabled: true
        postFunctions:
          - parameters:
              id: "<uuid>"
              config:
                className: "com.adaptavist.sr.cloud.workflow.UpdateIssue"
                uuid: "<uuid>"
                enabled: true
                executionUser: "ADD_ON"
                description: "Log transition"
                condition: "true"           # optional JEL guard
                additionalCode:
                  file: "<subdir>/<Script>.groovy"
```

In practice, use only the disambiguation fields you need — most transitions won't require `id`, and many won't need
`sourceStatus`/`targetStatus` if the name is unique.

#### Conditions

Conditions use **Jira Expression Language** and return a boolean. Two formats are supported:

**Flat conditions** (implicitly AND-ed at the root):

```yaml
conditions:
  - parameters:
      id: "<uuid>"
      config:
        uuid: "<uuid>"
        description: "<description>"
        expression: "(issue.assignee != null)"
        enabled: true
```

**Condition groups** (nested AND/OR logic):

```yaml
conditions:
  - parameters: # flat condition at root level
      id: "<uuid>"
      config:
        uuid: "<uuid>"
        description: "<description>"
        expression: "true"
        enabled: true
  - groups:
      - operation: "ANY"      # ANY = OR, ALL = AND
        conditions:
          - parameters:
              id: "<uuid>"
              config:
                uuid: "<uuid>"
                description: "<description>"
                expression: "true"
                enabled: true
        conditionGroups: # optional nested subgroups
          - operation: "ALL"
            conditions:
              - parameters:
                  id: "<uuid>"
                  config:
                    uuid: "<uuid>"
                    description: "<description>"
                    expression: "<JEL expression>"
                    enabled: true
```

Root conditions default to `ALL` (AND).

#### Validators

Validators use Jira Expression Language. When the expression returns `false`, the transition is blocked and
`errorMessage` is shown.

```yaml
validators:
  - parameters:
      id: "<uuid>"
      config:
        uuid: "<uuid>"
        description: "<description>"
        expression: "issue.summary.length >= 5"
        errorMessage: "<message shown to user when validation fails>"
        enabled: true
```

#### Post-functions

Post-functions execute Groovy scripts during transitions.

| `config` field          | Type          | Required           | Notes                                              |
|-------------------------|---------------|--------------------|----------------------------------------------------|
| `className`             | string        | **yes**            | `"com.adaptavist.sr.cloud.workflow.UpdateIssue"`   |
| `uuid`                  | string (UUID) | **yes**            | Identity field                                     |
| `enabled`               | boolean       | no                 | Default `true`                                     |
| `executionUser`         | string        | no                 | `"ADD_ON"` or `"INITIATING_USER"`                  |
| `condition`             | string        | no                 | Jira Expression; post-function runs only when true |
| `description`           | string        | no                 | Human-readable description                         |
| `additionalCode.file`   | string        | one of file/script | Groovy file relative to `cloud/src/main/groovy/`   |
| `additionalCode.script` | string        | one of file/script | Inline Groovy                                      |

```yaml
workflows:
  - name: "<Exact Workflow Name>"
    transitions:
      - name: "<Transition Name>"
        sourceStatus: "<fromStatus>"      # optional disambiguation
        targetStatus: "<toStatus>"
        type: "GLOBAL"                    # optional: DIRECTED, GLOBAL, INITIAL
        postFunctions:
          - parameters:
              id: "<uuid>"
              config:
                className: "com.adaptavist.sr.cloud.workflow.UpdateIssue"
                uuid: "<uuid>"
                enabled: true
                executionUser: "ADD_ON"
                description: "<description>"
                additionalCode:
                  file: "<subdir>/<Script>.groovy"    # prefer file over inline script
```

#### Rule ordering

By default, the order of conditions, validators, and post-functions follows their position in the YAML list — the first
item runs first.

Optionally, `postFunctions` and `validators` also support a `placement` block as a sibling of `parameters` (
see [README.md](README.md#ordering-post-functions-and-validators)):

| Field   | Type              | Notes             |
|---------|-------------------|-------------------|
| `index` | integer (0-based) | Absolute position |
| `first` | boolean           | Run first         |
| `last`  | boolean           | Run last          |

Only **one** placement field per rule. Only one rule per transition can use `first` or `last`.

```yaml
        postFunctions:
          - parameters:
              id: "<uuid>"
              config:
                className: "com.adaptavist.sr.cloud.workflow.UpdateIssue"
                uuid: "<uuid>"
                enabled: true
                executionUser: "ADD_ON"
                description: "<description>"
                additionalCode:
                  file: "<subdir>/<Script>.groovy"
            placement:
              first: true                   # or index: 2, or last: true
```

### Additional scripts (`additional-scripts`)

Scripts uploaded to Script Manager without being attached to any feature. Useful for shared library scripts imported by
other scripts.

| Field  | Type   | Required | Notes                                     |
|--------|--------|----------|-------------------------------------------|
| `file` | string | **yes**  | Path relative to `cloud/src/main/groovy/` |

```yaml
additional-scripts:
  - file: "<subdir>/<ScriptName>.groovy"
```

Deploy task name: `deploy-script-manager-<path-with-slashes-as-hyphens>` (e.g.
`deploy-script-manager-acme-dev-ConsoleScript1.groovy`).

### Validation checklist for generated configuration

Before proposing config changes, verify:

- [ ] Script file exists at the referenced path (or will be created alongside the YAML entry)
- [ ] Correct language for the feature (TypeScript for behaviours, Groovy for everything else)
- [ ] All required fields present with correct types
- [ ] UUIDs are valid and preserved for existing entries
- [ ] Only one script reference method per entry (`file`, `path`, or inline — not multiple)
- [ ] Workflow `name` matches the target Jira workflow exactly
- [ ] Transition disambiguation fields (`sourceStatus`, `targetStatus`, or transition `id`) are set when the transition
  name is not unique within the workflow
- [ ] Every condition, validator, and post-function has valid `parameters.id` and `config.uuid` values
- [ ] Post-function `className` is `"com.adaptavist.sr.cloud.workflow.UpdateIssue"`
- [ ] Behaviour `fieldName` is `""` and each `fieldUuid` is unique within the behaviour
- [ ] Behaviour names are globally unique
- [ ] Cron expressions use 6-field Quartz format
- [ ] `atlassianUser.accountId` is a real account ID or `%user-alias%` placeholder
- [ ] Project keys, issue type names, and field IDs use real values or `%alias%` placeholders

## Identifier Mappings

DC entity IDs (custom fields, users, issue types, etc.) don't carry over to Cloud as-is. Use `%alias%` placeholders in
scripts and `extensions.yaml`, defined in a mapping file at the project root. Run `./gradlew pullMappings` to resolve
them into a `mapped/<subdomain>/` folder; deploy tasks automatically use that folder when present.

See [MAPPING.md](MAPPING.md) for the full spec: mapping file format, placeholder syntax, resolution logic, supported
entity types, and validation rules.

## Deployment Commands

Requires JDK 17+. Authentication happens via browser popup (default) or API tokens in `~/.gradle/gradle.properties`.

```bash
# Bulk deployment
./gradlew cloud:deploy-all
./gradlew cloud:deploy-listener-all
./gradlew cloud:deploy-scriptField-all
./gradlew cloud:deploy-job-all
./gradlew cloud:deploy-behaviour-all
./gradlew cloud:deploy-workflow-all
./gradlew cloud:deploy-script-manager-all

# Individual deployment (name/description used as identifier)
./gradlew "deploy-listener-Add a comment on issue creation"
./gradlew "deploy-scriptField-Date Difference"
./gradlew "deploy-job-My Job Name"
./gradlew "deploy-behaviour-Test"
./gradlew "deploy-workflow-My Workflow Name"
./gradlew deploy-script-manager-acme-dev-ConsoleScript1.groovy
```

Listeners are identified by `description`. Script fields and jobs by `name`. Script Manager scripts by file path with
`/` replaced by `-`.

On Windows, use `gradlew.bat` instead of `./gradlew`.

## Supported Features

| Feature                    | Supported | Notes                                                      |
|----------------------------|-----------|------------------------------------------------------------|
| Listeners                  | Yes       |                                                            |
| Script Fields              | Yes       |                                                            |
| Jobs / Escalation Services | Yes       | Escalation services use `jobs` key with a `jql` field      |

| UI Fragments               | No        | Planned                                                    |
| JQL Functions              | No        | Planned                                                    |
| Built-in Scripts           | N/A       | Nothing to configure in Cloud                              |

## Important Constraints

- Workflows must already exist in the target Cloud instance (typically migrated via Jira Cloud Migration Assistant)
- Behaviours use TypeScript, not Groovy. Scripts go in `cloud/src/main/typescript/`
- Strongly prefer the `file` attribute over `path` for all features except behaviours (keeps scripts in Script Manager)
- Escalation services share the `jobs` YAML key but appear separately in the ScriptRunner Cloud UI
- Always remind users to replace placeholder account IDs, project keys, project IDs, and issue type IDs with real values
- YAML errors will be logged but the plugin will still try to create tasks for valid configurations
- The TypeScript compiler may emit expected warnings during behaviour compilation that can be safely ignored

## Updating the Plugin

Edit `settings.gradle` and change the version in:

```gradle
plugins {
    id 'com.adaptavist.scriptrunner.migration-settings' version '1.4.0'
}
```

Check
the [sample project on Bitbucket](https://bitbucket.org/adaptavistlabs/migration-example-project/src/main/settings.gradle)
or
the [Adaptavist Nexus repository](https://nexus.adaptavist.net/service/rest/repository/browse/external/com/adaptavist/scriptrunner/cloud/migration-dev-and-deployment-plugin/)
for the latest version.
